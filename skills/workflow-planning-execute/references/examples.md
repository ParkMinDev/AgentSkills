# 상황별 예시

가상의 런처 업데이트 프로젝트다. 문서 구성은 SKILL.md의 예시를 따른다.

## 1. 새 작업
사용자: "서버 그룹과 공개 함수 골격 작업계획을 저장해줘."
- `런처 API 골격 작업계획.md`를 만들고 전체 계획 '진행 중'에 링크를 단다. 고정 방침은 전체 계획에서 복사한다.
- 보고: "전체 계획을 수정했습니다." + 링크, "작업 계획을 생성했습니다." + 링크.

## 2. 고치기와 별도 작업
사용자: "작업계획에 서버 주소 변경 함수도 넣어줘. 진행 정보는 다음에 하자."
- 📦·📝·🔢·✅를 `SetServerGroup`이 들어간 최신 계획으로 다시 쓰고, 계획 요약에 "서버 주소 변경 함수 추가"를 적는다. 🤖도 맞춘다.
- 진행 정보 설계는 전체 계획 '남은 계획'에 둔다.

사용자: "그건 그대로 두고, 순서도 스킬 개선 계획을 별도로 만들자."
- 별도 작업계획 파일을 만든다. 런처 작업 파일과 합치지 않는다.

## 3. 채팅 계획에서 파일로
사용자: "복구 기능 계획 세워봐." → "2번은 사용자 지정 경로도 받게 바꿔서 다시 보여줘."
- 파일 개념이 없으므로 이 스킬의 대상이 아니다.

사용자: "좋아, 정한 대로 작업계획에 반영해줘."
- 채팅의 최신 계획으로 네 절을 다시 쓰고, 확정된 확인받을 것을 녹이고, 실행 전 상태는 `계획 중`으로 둔다. 파일이 없으면 새로 만든다.

## 4. 실행과 부분 완료
사용자: "이대로 시작해."
- 계획 파일이 있으므로 실행한다. 끝난 단계를 `[x]`로 바꾸며 진행한다.
- 클래스는 끝났지만 README가 남았다면 파일을 유지하고 남은 단계와 이유를 둔다. 전체 완료로 보고하지 않는다.

## 5. 검증 대기에서 완료로
- 런처 API 구현을 마쳤고 빌드 확인이 남았다면 작업계획의 사용자 메모 위에 다음 머리말을 둔다.

```markdown
작성일: 2026-11-25
상태: 검증 대기

## ✍️ 사용자 메모
```

- 전체 계획의 '진행 중'에 [[planning/런처 API 골격 작업계획]]을 연결하고, '✅ 검증'에는 빌드 확인을 남긴다. 빌드 요청만 보냈거나 오류가 발생했다면 이 상태를 유지한다.
- 이후 사용자가 검증을 요청해 계획한 검증이 모두 통과하면 상태를 `완료`로 바꾸고 파일을 옮긴다. 전체 계획의 '🏁 완료'에 빌드 결과와 [[planning/완료/런처 API 골격 작업계획]]을 기록한다.

## 6. 재개와 다음 작업
- "이제 다음 작업은?": 전체 계획 '남은 계획'에서 제안한다.
- "이전에 하던 작업 이어서": `완료/`가 아닌 작업계획을 읽고 이어서 실행한다. 후보가 여럿이고 문맥으로 특정되지 않을 때만 묻는다.
