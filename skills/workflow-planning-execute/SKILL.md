# 계획 파일 작성과 실행

구성은 아래 예시를 따른다. 예시는 가상이며 구성만 보여 준다.

## 예시

`<프로젝트명>.DevDocs/planning/전체 계획.md`:

```markdown
## ✍️ 사용자 메모

`<empty>`

<br>
## 📋 계획

### • 진행 중
- [ ] 저장 슬롯 백업 → [[planning/저장 백업 작업계획]]

### • 남은 계획
- [ ] 복원 화면 UI
      
<br>
## ✅ 검증
- [ ] 저장 경로 정리 — 이전 경로의 저장 파일 읽기 → [[planning/완료/저장 경로 작업계획]]
      
<br>
## 🏁 완료

### • 계획
- [x] 저장 경로 정리 — 구현 완료. 검증: 빌드 확인, 이전 경로 읽기는 남음 → [[planning/완료/저장 경로 작업계획]]

### • 검증
- [x] 저장 슬롯 이름 규칙 — 새 슬롯·기존 슬롯 불러오기 통과 → [[planning/완료/슬롯 이름 작업계획]]
      
<br>
## 📌 고정 방침
- 기존 데이터 마이그레이션은 하지 않는다.
  
<br>
## 🤖 에이전트 참고 영역
- 계획 문서 위치: `<프로젝트명>.DevDocs/planning/`
```

`<프로젝트명>.DevDocs/planning/저장 백업 작업계획.md`:

```markdown
작성일: 2026-11-25 · 상태: 확정. 구현 중. · 바뀐 점: 복원 경로 인자 추가

## ✍️ 사용자 메모
- [ ] 압축 형식 팀에 공유
      
<br>
## 📦 결과물
(show-result로 쓴다)

<br>
## 📝 계획 요약
- **저장 슬롯 자동 백업**: 저장할 때마다 직전 파일을 압축해 최근 5개만 보관한다.
- 남은 결정: 보관 개수를 설정으로 열지 → **열지 않는다** (삭제 규칙을 단순하게)
- 범위 밖: 복원 화면 UI
- 확인받을 것: 1. `Task<string>` 반환 2. 기존 `save.json.bak`은 읽지 않음
  
<br>
## 🔢 작업 순서
- [x] 1. `SaveBackupInfo`, `backups.json` 읽기·쓰기
- [ ] 2. `SaveStore.SaveAsync`에 직전 파일 백업과 보관 개수 정리
- [ ] 3. `SaveStore.RestoreBackupAsync`: 임시 해제 → 해시 비교 → 교체

<br>
## ✅ 검증
- [ ] 빌드 경고·오류 0
- [ ] 저장 7회 후 백업 5개
- [ ] 손상 백업 복원 시 기존 파일 유지
결과: 요청 없음 → 수행하지 않음

<br>
### 📌 고정 방침 — 전체 계획에서 가져옴
- 기존 데이터 마이그레이션은 하지 않는다.
  
<br>
## 🤖 에이전트용 계획
- 관련 코드: `SaveStore.cs`의 `SaveAsync`(지금은 `save.json.bak` 하나만 남김)
- 작업 조건: 스키마 1 유지, 커밋·푸시는 요청 시에만
- 전체 계획 원본: [[planning/전체 계획]]
```

## 적용 조건
- 요청에 **파일 개념**이 있거나 계획 파일을 실행하라고 할 때만 적용한다. 파일 개념이 없는 계획 요청("작업계획 세워봐")과 계획 파일이 없는 구현 요청은 대상이 아니다.
  - 명시: "파일", "문서", "md" 같은 말.
  - 암묵: "저장", "기록해", "남겨", "적어 둬"처럼 결과가 파일에 남는 동사.
  - 문서를 장소로 지목: "작업계획**에** 반영해줘", "전체 계획**에** 완료 표시해줘".
- 저장을 금지하거나 파일을 고치지 말라고 했으면 파일 작업을 하지 않는다.

| 요청 | 예 | 동작 |
| --- | --- | --- |
| 새 파일 | "작업계획 저장해줘", "이 계획 문서로 남겨줘" | 작업계획을 만들고 전체 계획 '진행 중'에 연결한다 |
| 고치기·반영 | "계획 파일에서 2번 빼줘", "정한 대로 작업계획에 반영해줘" | '갱신'을 따른다 |
| 실행 | "작업계획대로 진행해", "이 계획 실행해", "시작해" | '실행'을 따른다 |
| 완료 기록 | "전체 계획에 완료 반영해줘" | '완료'를 따른다 (작업계획은 `완료/`로 옮김) |

## 문서
- 두 문서 모두 맨 위에 **✍️ 사용자 메모**를 둔다. 사용자의 체크리스트와 메모를 두는 곳이다. 에이전트는 계획을 고치거나 실행하기 전에 읽고, 사용자가 요청할 때만 고친다. 메모가 계획과 어긋나면 고치기 전에 묻는다.
- **표기**: 대단원은 아이콘을 붙인 `##`, 그 아래 묶음은 `### • 이름`이다. 다른 대단원과 같은 것을 가리키는 소제목(고정 방침 사본)은 그 아이콘을 쓴다. 첫 대단원을 뺀 대단원 앞에는 앞 내용 뒤에 빈 줄 하나를 두고 `<br>`을 쓴 다음, 그 바로 다음 줄에 대단원을 쓴다(Obsidian은 빈 줄을 합쳐 간격이 생기지 않음). 내용이 없는 절에는 `` `<empty>` ``를 둔다(소제목을 가진 대단원은 제외).
- **전체 계획.md**는 프로젝트마다 하나다. 대단원은 ✍️ → 📋 계획 → ✅ 검증 → 🏁 완료 → 📌 고정 방침 → 🤖 에이전트 참고 영역 순서다.
  - 📋 계획: 진행 중은 작업계획이 있는 작업, 남은 계획은 아직 작업계획이 없는 후속 작업이다.
  - ✅ 검증: 구현은 끝났지만 아직 수행하지 않은 검증만 둔다.
  - 🏁 완료: 끝난 것을 한 줄씩 쌓는다. '계획'에는 끝난 작업을 구현 내용과 그때의 검증 결과와 함께, '검증'에는 나중에 수행한 검증을 결과와 함께 둔다. ✅ 검증의 항목을 수행하면 그 줄을 지우고 '검증'에 옮긴다.
  - 📌 고정 방침이 공통 원본이고, 🤖 에이전트 참고 영역은 내용이 적어도 항상 둔다.
- **<작업명> 작업계획.md**는 작업마다 하나다. 완료되면 `planning/완료/`로 옮긴다.
  - 📦 결과물은 [show-result](../show-result/SKILL.md)를 따른다. 결과물이 없는 작업은 목적·범위·대상·완료 조건을 쓴다.
  - 🔢 작업 순서에는 실제 타입·함수·파일 이름을 쓰고, 문서·순서도 갱신도 한 항목으로 둔다.
  - ✅ 검증에는 확인할 항목을 미리 적고, 실제로 수행한 항목만 `[x]`로 바꾼다. 마지막 줄에 결과(수행 범위, 또는 요청 없음 → 수행하지 않음)를 적는다.
  - 📌 고정 방침 사본은 ✅ 검증과 🤖 사이에 `###` 소제목으로 두고, 앞에 다른 대단원처럼 `<br>`을 둔다.
  - 📝·🤖의 형식은 에이전트 재량이다. 채팅에서 보여 준 계획이 있으면 그 내용을 옮긴다.
- 위치는 사용자가 지정한 곳을 우선하고, 기본은 AGENTS.md 개발 문서 보관소 규칙의 `<프로젝트명>.DevDocs/planning/`이다.
- 기존 전체 계획과 작업 파일을 먼저 찾고 같은 문서를 중복 생성하지 않는다. `완료/` 안의 파일은 끝난 기록이라 고치지 않고, 이어서 할 작업을 찾을 때 건너뛴다. 같은 작업을 다시 하면 새 작업계획을 만든다. 전체 계획이 없으면 사용자·저장소 지침과 명시적으로 합의한 범위로 만든다. 스킬이 바뀌었다고 기존 계획 파일을 일괄 이동·삭제하지 않는다.

## 갱신
- 최신 내용은 요청에 다 있으면 요청에서, "정한 대로", "방금", "확정한"처럼 대화에서 정한 것을 옮기라는 뜻이면 채팅의 최신 계획에서 가져온다.
- **📦·📝·🔢·✅는 최신 계획으로 통째로 다시 쓴다.** 일부만 고치라는 요청이어도 네 절 전체를 맞춘다. 작업 순서와 검증의 `[x]`, 검증 결과는 그대로 옮긴다.
- **🤖는 최신 계획에 맞게 고치고, 맞지 않게 된 항목은 지운다.**
- **✍️ 사용자 메모는 다시 쓰지 않고 그대로 둔다.** 완료 폴더로 옮길 때도 그대로 간다.
- 다시 쓸 때마다 머리의 상태와 바뀐 점 한 줄을 갱신한다. 확정된 확인받을 것은 해당 절에 녹이고, 확정되지 않은 제안은 제안으로 남긴다.
- 대상 계획 파일이 없으면 새로 만든다. 후보가 여러 개이고 문맥으로 특정되지 않을 때만 묻는다.

## 진행 원칙
- 한 작업의 계획은 단계로 쪼개지 않는다. 한 번에 확인받고, 확정되면 한 번에 구현한다. 결과물이 이어진 두 기능은 한 계획에 둔다.
- 같은 작업의 보충이면 기존 파일을 갱신하고, 독립 작업은 새 파일을 만든다. 이름이 겹치면 구체적인 작업명을 쓰고, 다른 작업 계획을 자동으로 합치지 않는다.
- 범위에서 빠진 작업과 앞으로 필요한 합의는 전체 계획 '남은 계획'으로 옮긴다. 다음 작업을 물으면 '남은 계획'에서 제안하고, 파일을 미리 만들지 않는다.
- 전체 계획의 고정 방침이 원본이다. 작업을 시작·재개하거나 공통 방침이 바뀌면 전체 계획부터 고치고 작업계획의 사본을 맞춘다. 이번 작업만의 예외는 🤖의 작업 조건에 두고 공통 방침으로 올리지 않는다.
- 설명만 요청했다면 파일을 고치지 않는다.

## 실행
계획 파일에 항목이 있다는 것은 실행·삭제·커밋·푸시·배포 승인이 아니다. 사용자가 실행하라고 했을 때만 시작한다.
1. 계획 파일을 다시 읽고 고정 방침 사본을 원본과 맞춘다.
2. 남은 결정이나 확인받을 것이 있으면 실행하지 않고 그것부터 묻는다.
3. 상태를 "확정. 구현 중."으로 바꾸고 작업 순서대로 한 번에 구현한다. 끝난 단계는 `[x]`로 바꾼다.
4. 계획과 달라진 점(이름, 순서, 범위)은 '갱신'으로 반영한다. 범위를 넓혀야 하면 멈추고 묻는다.
5. 검증은 사용자의 검증 지시가 있을 때만 하고, ✅ 검증의 수행한 항목과 결과를 갱신한다.
6. 일부만 끝났으면 남은 단계와 막힌 이유를 남기고 파일을 유지한다. 다 끝났으면 '완료'로 넘어간다.

## 완료
1. 요청받은 구현·검증이 남아 있으면 미완료다. 실행하지 않은 검증을 통과로 적지 않는다.
2. 계속 필요한 설명은 코드나 프로젝트 문서에 남긴다.
3. 상태를 "완료."로 바꾸고 작업계획.md를 `planning/완료/`로 옮긴다(같은 이름이 있으면 날짜를 붙인다). 연결된 표·순서도·데이터 노트는 그대로 둔다.
4. 전체 계획에서 해당 항목을 🏁 완료의 '계획'으로 옮겨 `[x]`로 두고, 구현 내용과 ✅ 검증 결과를 한 줄로 적고, 옮긴 작업계획을 링크한다. 큰 기능의 일부만 끝났으면 세부 항목만 옮긴다.
5. 작업계획의 ✅ 검증에서 수행하지 않은 항목은 전체 계획 ✅ 검증으로 옮긴다. `완료/` 파일은 고치지 않으므로, 옮기지 않으면 남은 검증이 보이지 않게 된다.
