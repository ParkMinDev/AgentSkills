# View Model Composition

## 요청 해석과 범위
- View(뷰)는 화면 표현, Model(모델)은 상태와 규칙, Runner(러너)는 실행 조정, Binder(바인더)는 유지되는 연결을 담당한다.
- 먼저 기존 코드와 프로젝트 지침에서 대상, 화면 체계, 사용 가능한 비동기·구독 라이브러리, 기존 조립 지점을 확인한다.
- 요청한 역할만 우선 구현하고 기존 구성요소를 재사용한다. 역할마다 새 클래스를 일괄 생성하거나 기존 프레젠터를 일괄 교체하지 않는다.
- 이 스킬 문맥에서 “뷰 모델”은 기본적으로 뷰와 모델의 조합이다. 화면 전용 상태 객체인 ViewModel을 명시하거나 기존 프로젝트가 그 의미로 사용하면 그 문맥을 따른다. 의미가 불명확하고 설계에 영향을 줄 때만 확인한다.
- 질문·설계 설명만 요청하면 코드나 에셋을 변경하지 않는다.

| 요청 | 기본 구현 범위 |
| --- | --- |
| 뷰 만들어줘 | 표시·입력·연출과 필요한 표시용 메서드 |
| 모델 만들어줘 | 상태·규칙과 필요한 상태 변경 메서드 |
| 뷰 모델 만들어줘 | 뷰와 모델, 필요한 최소 연결은 기존 상위 로직 활용 |
| 뷰 모델 러너 구조로 만들어줘 | 뷰·모델과 완료가 있는 실행 흐름 |
| 뷰 모델 바인더 구조로 만들어줘 | 뷰·모델과 초기 표시 및 지속적인 연결 |
| 러너 바인더 모두 사용해줘 | 순차 실행과 유지되는 연결을 분리 |

- 뷰·모델만 요청했다고 러너나 바인더를 자동 생성하지 않는다. 통합 실행까지 요청했는데 기존 조립 지점이 없으면 필요한 최소 조립 책임을 명시해 구현한다.
- 공통 책임 분리는 Unity 밖에서도 적용한다. 아래 Unity 타입 관련 제한은 다른 환경에서도 도메인 객체를 표시 객체로 우회 전달하지 않는 원칙으로 적용한다.
- C# 작성에는 사용 가능한 csharp-project-style 지침을 따른다. Unity 화면 작업은 사용 가능한 ui 및 해당 화면 체계의 스킬을 함께 적용한다. Unity 에디터 조작은 프로젝트의 Unity CLI 지침과 unity-cli를 따른다.

## 뷰 구현규칙

- 뷰(View)는 자신의 화면 표시에 필요한 Unity 컴포넌트·에셋과 자식 뷰를 참조한다.
- 다른 독립 화면이나 부모·형제 뷰를 직접 참조하여 제어하지 않는다. 화면 간 연결은 프레젠터·Feature·디렉터 등 외부 로직에서 담당한다.
- 게임 모델·게임 Actor·네트워크 객체·원본 통신 데이터·카탈로그를 직접 참조하거나 조회하지 않는다. 이 제한은 필드뿐 아니라 메서드 매개변수에도 적용한다.
- 게임 Actor를 GameObject나 Transform으로 전달하여 위 제한을 우회하지 않는다.
- 모델 해석·카탈로그 조회·게임 규칙·권한 판단·도메인 계산은 외부 로직에서 수행하고, 뷰에는 표시에 필요한 문자·숫자·색상·불리언·에셋 등의 값만 전달한다.
- 좌표와 시간처럼 표시만을 위한 단순 데이터 구조와 읽기 전용 목록은 사용할 수 있다. 이를 이유로 원본 게임 모델 전체를 전달하지 않는다.
- 표시 형식 변환·아이콘과 색상 선택·레이아웃·애니메이션·자식 뷰 연출·화면 내부 입력 요소의 연동은 뷰에서 처리할 수 있다.
- 분리를 위해 불필요한 전달용 클래스나 프레젠터를 일괄 생성하지 않고, 기존 연결 로직을 우선 활용한다.

## Feature 역할

- Feature는 로직을 컴포넌트 형태로 구성한 것이며 뷰로 분류하지 않는다.
- Feature에는 뷰의 모델 참조 제한을 적용하지 않는다. 담당 기능에 필요한 모델·Actor 등을 참조할 수 있다.

## 모델
- 실제 상태와 도메인 규칙을 담당하며 뷰·러너·바인더를 참조하지 않는다.
- 기존 모델과 서비스를 우선 사용하고, 화면 연결을 위해 원본 모델을 복제한 공용 전달 객체를 만들지 않는다.
- 상태 변경은 필요한 메서드로 표현한다. 지속적인 변경 통지가 필요한 경우에만 프로젝트의 이벤트·관찰 가능한 상태 방식을 사용한다.
- 화면 전용 ViewModel이 명시적으로 필요하면 표시 상태에 책임을 한정하고 원본 모델과 중복 상태의 갱신 책임을 분명히 한다.

## 러너
- 시작과 완료가 있는 흐름을 명시적인 실행 메서드로 제공한다. 입력 대기 → 모델 또는 서비스 작업 → 결과 표시 → 연출 완료처럼 호출과 await로 순서를 드러낸다.
- 완료를 기다려야 하는 작업을 이벤트 구독이나 IDisposable 반환만으로 대체하지 않는다. 작업 전체를 생성자나 구독 콜백에 숨기지 않는다.
- 취소·예외·정상 완료 시 필요한 정리를 수행한다. 중복 실행 가능성을 확인하고 요청 거절·기존 실행 취소·순차 처리 중 해당 기능에 맞는 정책을 정한다.
- 표현 연출은 뷰에 맡기고 흐름상 필요할 때 그 완료를 기다린다. 도메인 규칙은 모델이나 기존 서비스에 맡긴다.
- 실행 중 필요한 구독은 실행 범위 안에서 관리하고 완료·취소·예외 시 해제한다.

## 바인더
- 모델 상태를 해석해 뷰의 표시값으로 전달하고 일정 기간 유지되는 상태·이벤트 연결을 관리한다.
- 연결 시 현재 상태도 표시한다. 변경 통지만 구독하여 첫 표시가 누락되지 않도록 한다.
- 장기간 연결할 필요가 없는 순차 비동기 작업을 바인더에 몰아넣지 않는다. 단순 입력 전달은 가능하지만 복잡한 실행 흐름은 러너나 기존 외부 로직이 담당한다.
- 같은 입력이나 표시값을 러너와 바인더가 중복 처리하지 않도록 책임을 하나로 정한다. 양방향 연결이 필요하면 피드백 반복을 막는다.
- 연결 시작과 해제 시점을 명확히 한다. 생성자에서 연결할지 명시적 연결 메서드를 둘지는 기존 구조와 필요한 수명에 맞춘다. 재연결 시 구독이 중복되지 않게 한다.
- R3 사용 시 구독을 CompositeDisposable 등에 등록하고, 일반 C# 이벤트는 해제할 핸들러를 보관한다. 연결 종료 시 모든 구독을 해제한다.

## 조립과 수명
- 기존 상위 객체(화면 컨트롤러, Feature 등)가 필요한 뷰·모델·서비스를 준비해 러너·바인더에 전달하고 실행과 연결 수명을 관리한다.
- 러너·바인더 안에서 주입받아야 할 뷰나 모델을 임의로 생성하지 않는다. 필요한 구체 참조만 전달한다.
- 종료 시 실행을 취소하고 사용 중인 자원에 접근하지 않도록 흐름을 정리한 뒤 연결과 소유 자원을 해제한다. 해제 책임은 한곳에 둔다.
- IDisposable은 해제할 구독·자원이 있을 때 적용하고 프로젝트의 기존 수명 관리 방식도 활용한다. sealed, 공개 멤버를 생성자·Dispose로 제한하는 규칙, 생성자 람다 구독을 일괄 강제하지 않는다.
- Presenter(표시 내용 구성자), Coordinator(여러 흐름의 조정자), Service(공유 기능), Navigator(화면 이동 담당자)는 실제 책임 분리가 필요할 때만 추가한다.

## Unity uGUI 계층 구성
- 아래 규칙은 Canvas·GameObject·RectTransform 기반 uGUI에만 적용한다. UI Toolkit이나 비Unity 화면에는 해당 체계의 구성 방식을 따른다.
- UI는 화면의 포함 관계와 기능 단위가 GameObject의 부모·자식 계층에 드러나도록 구성한다.
- 큰 UI 영역을 부모로 두고, 그 영역에 속하는 작은 UI 요소들을 자식으로 배치한다. 예를 들어 참가자 카드의 이름·아이콘·버튼은 해당 카드의 자식으로, 버튼의 글자·아이콘은 해당 버튼의 자식으로 둔다.
- 관련 요소들을 Canvas 바로 아래에 나열하지 않고, 함께 이동·표시·숨김 처리할 단위로 묶는다.
- 자식 UI의 RectTransform은 부모 영역을 기준으로 배치한다.
- 단순히 크기가 크거나 화면에서 겹친다는 이유만으로 부모·자식 관계를 만들지 않는다. 독립적인 팝업처럼 별도 표시 계층이 필요한 요소는 분리한다.
- 불필요한 중간 GameObject나 과도한 중첩은 만들지 않는다.
