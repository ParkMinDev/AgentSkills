# 프로젝트 작업 계획 관리

## 적용 조건

- 사용자 요청에 “저장”이라는 단어가 있고 전체 계획이나 작업계획을 저장하라는 뜻일 때만 이 스킬을 적용한다. “작업계획 저장해줘”, “전체 계획에 저장해줘”가 해당한다.
- “계획 세워봐”, “계획을 보여줘”, “계획대로 시작해”는 일반 요청으로 처리한다. 단순히 “저장”을 언급하거나 저장을 금지하는 요청도 발동 조건에 해당하지 않는다.


## 문서의 역할과 위치
- 프로젝트마다 **전체 계획.md** 하나를 유지한다. 큰 기능 체크리스트, 후속 작업, 확정된 설계 사항, 구현·검증 상태와 완료 기록을 보관한다. 공통 **고정 방침은 문서 맨 아래**에 둔다.
- 구체적인 작업마다 **<작업명> 작업계획.md**를 만든다. 목적·범위·대상 파일/함수·순서·미확정 사항·완료 조건을 기록하고, 전체 계획에서 가져온 고정 방침을 맨 아래에 둔다. 완료하면 내용을 비워 재사용하지 않고 해당 파일을 삭제한다.
- 먼저 대상 프로젝트와 적용되는 사용자·저장소 지침을 확인한다. 기존 전체 계획과 현재 요청에 해당하는 작업 파일을 찾고, 같은 문서를 중복 생성하지 않는다.
- 사용자가 지정한 파일과 위치를 우선한다. 기본 위치는 대상 프로젝트 루트의 `Work/planning/`이다. Unity 프로젝트도 같은 위치를 사용한다. 계획 문서는 버전 관리 대상으로 두고, 테스트 빌드와 원시 로그는 프로젝트의 산출물 위치에 보관한다.
- 전체 계획이 없다면 사용자·저장소 지침과 명시적으로 합의한 범위로 만든다. 다른 프로젝트의 방침을 가져오거나 확인되지 않은 정책을 고정하지 않는다.
- 기존 단일 작업 계획에 미완료 내용이 있으면 보존하고 해당 작업 파일로 계속 사용하거나 요청 범위에 맞게 정리한다. 스킬 변경만으로 기존 파일들을 일괄 이동·삭제하지 않는다.

## 문서 구성과 변경 강조

- 전체 계획과 개별 작업계획 모두 제목 아래에 `## - 사람이 읽는 영역 -`, 이어서 `## - 에이전트 참고 영역 -`을 둔다. 기존 문서는 요청받은 갱신 범위에서 이 형식으로 정리한다.
- 사람용 영역은 `explain-code-changes` 스킬을 적용해 목적과 현재 상태, 결정 이유, 남은 작업을 먼저 설명한다. 코드 변경은 대상과 실제 전후 동작을 연결하고, 설계 단계에서는 제안·확정·완료를 구분한다. 전체 계획은 주요 기능의 진행 상태를, 개별 계획은 작업 범위와 완료 조건을 보여준다.
- 측정 결과가 있으면 사람용 영역의 비교표 하나에 모은다. 이전·최신 수치를 함께 제시할 때는 측정 기준을 표시한다. 에이전트 영역에는 실제 대상, 구현 순서, 제약, 재현 절차와 원본 링크를 둔다. 고정 방침은 이 영역의 맨 아래에 둔다.
- 최초 작성에는 변경 강조를 넣지 않는다. 갱신할 때는 수정 직전 문서에서 이전 변경 강조를 걷어내고, 사람용 영역의 이번에 추가·변경된 문구나 표 셀만 강조한다. 제목 이동, 서식 변경만으로는 강조하지 않는다. 기존 의미상 강조는 유지한다.
- 대상 화면의 HTML 글자색 지원을 확인했으면 색을 쓰고, 지원하지 않거나 확인할 수 없으면 Markdown 굵게를 사용한다. 삭제는 본문에서 반영하고, 알아야 할 삭제만 사람용 영역에 짧게 알린다. 에이전트 영역에는 변경 강조를 적용하지 않는다.

## 작업 선택과 독립성
- 사용자가 파일을 지정하면 그 파일을 사용한다. “이 작업 이어서”처럼 문맥이 명확하면 해당 작업 파일을 선택한다. 후보가 여러 개여서 구분되지 않을 때만 확인한다.
- 같은 작업의 보충·수정이면 기존 파일을 갱신한다. 독립 작업은 새 파일을 만들고 기존 작업 파일을 유지한다. 이름이 겹치면 구체적인 작업명을 사용하며 기존 파일을 덮어쓰지 않는다.
- 다른 프로젝트나 같은 채팅의 별도 작업 계획을 자동으로 합치지 않는다. 목록의 첫 파일이나 최신 파일을 무조건 선택하지 않는다.
- 다음 작업 조회에는 전체 계획의 미완료 항목을 근거로 제안한다. 구체적인 계획 수립이나 작업 시작을 요청하지 않았다면 새 작업 파일을 만들지 않는다.

## 고정 방침의 원본과 사본
- 전체 계획의 고정 방침이 프로젝트 공통 원본이다. 작업 파일 생성 시 해당 방침을 맨 아래에 복사하고 원본 전체 계획의 경로를 기록한다.
- 작업을 재개할 때 원본과 비교해 변경된 방침을 반영한다. 사용자가 공통 방침을 바꾸면 전체 계획부터 갱신하고 현재 작업의 사본도 갱신한다. 별도 실행 중인 다른 작업 파일을 무조건 일괄 수정하지 않는다.
- 이번 작업에만 적용하는 조건·예외는 작업 범위에 기록한다. 이를 공통 방침으로 승격하지 않는다. 새 사용자 지시와 상위 지침이 문서보다 우선한다.

## 계획 수립과 진행
- 전체 계획의 관련 항목 및 고정 방침을 먼저 읽는다. 이번 작업의 목적·범위·제외 범위, 실제 파일·클래스·함수, 구현 순서와 완료 조건을 구체화한다.
- 확정 사항과 제안을 구분한다. 미확정 제안을 승인받은 것처럼 구현하거나 고정 방침으로 기록하지 않는다.
- 범위가 바뀌면 모순되는 이전 항목을 정리한다. 미뤄진 작업과 필요한 합의는 전체 계획에 옮긴 후 현재 작업에서 제거한다.
- 부분 완료이면 파일을 유지한다. 완료한 세부 항목을 정리하되 남은 작업의 의존 정보·제약과 막힌 이유를 보존한다. 별도 개선 사항을 발견해도 요청 범위에 자동으로 포함하지 않는다.
- 계획 문서에 항목이 있다는 사실은 실행·삭제·커밋·푸시·배포 승인이 아니다. 계획 기록과 제품 코드 구현을 구분하고 사용자의 실행 범위를 따른다.
- 설명만 요청했거나 파일을 수정하지 말라고 했다면 그 제약을 우선한다.

## 완료와 작업 파일 삭제
1. 해당 작업의 완료 조건을 확인한다. 요청받은 구현·검증이 남아 있으면 미완료이며 파일을 삭제하지 않는다.
2. 후속 작업·미완료 검증·앞으로 필요한 합의를 전체 계획에 보관한다. 계속 필요한 상세 구현 설명은 코드나 프로젝트 문서에 남긴다.
3. 전체 계획에서 완료한 항목을 **[x]로 표시하고 유지**한다. 구현 내용과 실제 검증 여부를 짧게 기록한다. 큰 기능의 일부만 끝났으면 세부 항목만 완료 표시하고 큰 항목은 [ ]로 유지한다.
4. 사용자가 검증을 요청하지 않아 생략했다면 이를 명시하고 구현 작업은 완료 처리할 수 있다. 요청받은 검증이 미완료라면 작업도 완료가 아니다. 실행하지 않은 검증을 통과로 기록하지 않는다.
5. 작업 파일에만 남은 필요한 정보가 없는지 확인하고, 대상의 절대 경로를 확인한 뒤 **해당 작업계획.md 파일 하나만 삭제**한다. 전체 계획·고정 방침·다른 작업 파일은 삭제하지 않는다.
- 작업 파일을 지우기 위해 완료 조건을 낮추지 않는다. 보류·중단·부분 완료 상태에서는 유지한다. 사용자가 완료 후에도 보관하라고 하면 삭제하지 않는다.

## 파일 변경 보고
실제 수행한 문서 작업을 최종 응답에 명시한다. 여러 개면 각 파일을 구분한다.
- 전체 계획 생성·수정: “전체 계획을 생성/수정했습니다.”와 해당 파일 링크.
- 개별 작업 계획 생성: “작업 계획을 생성했습니다.”와 해당 파일 링크.
- 개별 작업 계획 수정: “작업 계획을 수정했습니다.”와 해당 파일 링크.
- 개별 작업 계획 삭제: “작업 계획을 삭제했습니다.”와 삭제한 파일명 또는 절대 경로. 삭제된 파일에는 링크를 붙이지 않는다.
- 읽기만 한 문서를 수정했다고 보고하지 않는다. 한 작업에서 생성 후 삭제했다면 두 동작을 밝히되 삭제된 파일을 생성 링크로 남기지 않는다.
- 구현 완료와 검증 완료를 구분해 실제 수행/생략 여부를 보고한다.

## 예시
문서 형태, 병행 작업, 부분 완료 및 완료 후 삭제 판단은 [references/examples.md](references/examples.md)를 참고한다. 예시의 프로젝트와 정책은 설명용이며 다른 프로젝트에 강제하지 않는다.
