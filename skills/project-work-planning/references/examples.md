# 전체 계획과 작업별 계획 예시

가상의 업데이트 프로젝트 예시다. 마이그레이션 금지와 검증 방침은 이 프로젝트 사용자가 명시적으로 합의했다고 가정한다.

## 1. 새 작업 생성

사용자: “업데이트 기능에서 서버 그룹과 공개 함수 골격 작업계획을 저장해줘.”

전체 계획.md:

```markdown
# 전체 계획

## - 사람이 읽는 영역 -

## 런처 업데이트
- [ ] 런처 자체 업데이트 완성
  - [ ] 서버 그룹·공개 함수 골격
  - [ ] 통신·다운로드·검증
  - [ ] 파일 교체·재실행

## - 에이전트 참고 영역 -

### 고정 방침
- 기존 데이터 마이그레이션은 하지 않는다.
- 빌드·실행 검증은 별도 요청이 있을 때 수행한다.
```

새 파일 런처 API 골격 작업계획.md:

```markdown
# 런처 API 골격 작업 계획

## - 사람이 읽는 영역 -

서버 주소를 등록하고 업데이트 함수를 호출할 수 있게 API의 골격을 만든다. 공개 선언과 호출 예시가 일치하면 완료한다.

## - 에이전트 참고 영역 -

전체 계획 원본: ./전체 계획.md

### 목적과 범위
- ServerGroup.cs: 주소 검사·정규화.
- Launcher.cs: 공개 선언과 중첩 업데이터 연결.
- README.md: 실제 선언과 일치하는 호출 예시.
- 제외: 실제 통신·종료·파일 교체.

### 구현 확인
- 공개 함수 골격과 호출 예시를 구현한다.
- 실행 함수는 미구현 예외를 전달하며 통신·종료 부수 효과가 없다.

### 고정 방침 — 전체 계획에서 가져옴
- 기존 데이터 마이그레이션은 하지 않는다.
- 빌드·실행 검증은 별도 요청이 있을 때 수행한다.
```

보고: “전체 계획을 수정했습니다.” + 전체 계획 링크. “작업 계획을 생성했습니다.” + 새 파일 링크.

## 2. 같은 작업 변경과 별도 작업

사용자: “서버 주소 변경 함수도 넣자. 진행 정보는 다음에 하자.”
- 같은 작업 파일에 SetServerGroup을 반영한다.
- 진행 정보 설계는 전체 계획에 후속 작업으로 남긴다.
- 두 파일을 수정했다면 각각 수정 사실과 링크를 보고한다.

사용자: “그건 그대로 두고, 순서도 스킬 개선 계획을 별도로 만들자.”
- 대상 스킬 저장소에 순서도 개선 작업계획.md를 만든다.
- 기존 프로젝트의 런처 작업 파일과 전체 계획은 수정하지 않는다.
- 같은 프로젝트 안의 독립 작업이어도 파일을 따로 만든다.
- 현재 어느 작업을 이어갈지 불명확할 때만 확인한다.

## 3. 부분 완료와 방침 변경

클래스는 구현했지만 README가 남았다면 런처 API 골격 작업계획.md를 유지한다.

```markdown
## 남은 작업
- README 호출 예시를 실제 공개 선언에 맞춰 갱신.
- 실행 함수가 통신·종료를 수행하지 않는다는 범위는 유지.
```

이 예시는 일부 영역만 발췌했다. 원본 전체 계획 참조와 맨 아래 고정 방침은 지우지 않는다. 전체 완료로 보고하거나 작업 파일을 삭제하지 않는다.

사용자가 공통 방침을 바꾸면 전체 계획의 원본과 현재 작업의 사본을 함께 갱신한다. 이번 작업만 검증하라는 지시는 작업 조건에 적으며 공통 검증 방침을 임의로 변경하지 않는다.

## 4. 작업 완료와 파일 삭제

골격·문서 작업이 완료됐다면 전체 계획에 남긴다.

```markdown
## 런처 업데이트
- [ ] 런처 자체 업데이트 완성
  - [x] 서버 그룹·공개 함수 골격
    - 구현: 주소 검사·공개 함수·호출 예시 반영.
    - 검증: 요청이 없어 빌드·실행 검증은 수행하지 않음.
  - [ ] 통신·다운로드·검증
  - [ ] 파일 교체·재실행
  - [ ] 진행 정보 설계

## 확정 사항
- 준비 실패 시 종료 콜백을 호출하지 않는다.

## 고정 방침
- 기존 데이터 마이그레이션은 하지 않는다.
- 빌드·실행 검증은 별도 요청이 있을 때 수행한다.
```

필요한 정보가 전체 계획과 문서에 남았는지 확인한 뒤 런처 API 골격 작업계획.md만 삭제한다. 런처 전체 업데이트 항목은 아직 미완료다. 완료한 골격 기록은 전체 계획에서 삭제하지 않는다.

보고:
- “전체 계획을 수정했습니다.” + 존재하는 전체 계획 파일 링크.
- “작업 계획을 삭제했습니다: 런처 API 골격 작업계획.md.” 삭제 파일에는 링크를 붙이지 않는다.
- 구현 완료와 검증 생략을 구분한다.

검증까지 요청받았는데 검증이 남았다면 파일을 유지하고 미완료라고 보고한다.

## 5. 재개·다음 작업 조회·기존 파일

- “이제 다음 작업은?”: 전체 계획의 미완료 항목을 읽고 제안한다. 다음 작업 파일을 미리 만들지 않는다.
- “통신 작업 계획을 저장해줘”: 통신 작업계획.md를 만들며 고정 방침을 전체 계획에서 가져온다.
- “이전에 하던 작업 이어서”: 해당 파일을 읽고 전체 계획의 최신 방침을 반영한다. 후보가 여러 개이고 문맥으로 특정되지 않을 때만 확인한다.
- 기존 작업 계획.md에 미완료 병렬 복사 계획이 있다면 보존한다. 새 스킬 규칙을 적용한다는 이유로 삭제하지 않는다.
- 단순 함수 이름 질문에는 설명만 한다. 계획 문서 생성·수정을 강제하지 않는다.

## 6. 측정 결과 갱신

최초 작성에서는 `206.9ms`를 일반 텍스트로 적는다. 재측정하여 값이 바뀌면 사람용 표에서 새 값만 강조한다. 아래는 글자색 지원을 확인할 수 없는 화면의 예시다.

```markdown
## - 사람이 읽는 영역 -

| 시나리오 | 적용 전 | 적용 후 | 조건 |
|---|---:|---:|---|
| 동일 버전 빠른 검사 | 206.9ms | **161.8ms** | 같은 골프 사본, 로컬 |

## - 에이전트 참고 영역 -

- 예열 후 실행 순서를 교대해 각 모드 10회 측정. 원본은 결과 파일에 보관.
```

다음 갱신에서는 `161.8ms`의 변경 강조를 걷어내고 그때 바뀐 부분만 강조한다.
