# 두 계획 문서의 사용 예시

가상의 앱 업데이트 프로젝트 예시다. 마이그레이션 금지와 검증 방침은 이 예시의 사용자가 별도로 합의했다고 가정한다.

## 1. 새 작업 계획

사용자: “업데이트 기능에서 서버 그룹 클래스와 공개 함수 골격부터 만들어줘.”

전체 계획.md:

```markdown
# 전체 계획

- [ ] 런처 자체 업데이트
  - 다음 단계: 서버 통신, 다운로드·검증, 파일 교체.
- [ ] 앱 설치·실행
```

작업 계획.md:

```markdown
# 작업 계획

## 현재 작업: 런처 API 골격

- ServerGroup.cs: 주소 검사·정규화 구현.
- Launcher.cs: 생성자와 중첩 업데이터 연결.
- 실행 함수는 미구현 예외를 던지도록 선언.
- 완료 조건: 공개 선언과 호출 예시 일치, 실제 통신·종료 부수 효과 없음.
- 제외: 다운로드·파일 교체·앱 설치.

## 고정 방침

- 기존 데이터 마이그레이션은 하지 않는다.
- 빌드·실행 검증은 별도 요청이 있을 때 수행한다.
```

## 2. 작업 범위 변경

사용자: “서버 주소를 바꾸는 함수도 넣자. 진행 정보 필드는 다음에 정하자.”

- 현재 작업에 SetServerGroup 선언·주소 복사 규칙을 반영한다.
- 진행 정보 필드 설계를 현재 작업에서 빼고 전체 계획의 런처 업데이트 항목에 남긴다.
- 미뤄진 필드를 완성하거나 삭제된 계획을 계속 구현하지 않는다.
- 지속 정책이 아니므로 이번 함수 추가를 고정 방침에 넣지 않는다.

## 3. 부분 완료

클래스는 구현했지만 요청 범위에 있던 호출 예시 문서는 아직 수정하지 못했다면:

```markdown
## 현재 작업: 런처 API 골격

- 남은 작업: README 사용 예시를 실제 공개 선언에 맞춰 갱신.
- 유지할 제약: 실행 함수는 미구현 예외를 던지며 실제 통신·종료는 하지 않음.
```

큰 체크리스트의 런처 자체 업데이트는 여전히 미완료다. 현재 작업을 비우고 완료했다고 보고하지 않는다.

## 4. 이번 작업 최종 완료

API 골격과 문서 정리가 모두 끝났다면 전체 계획에 다음 내용을 남긴다.

```markdown
- [ ] 런처 자체 업데이트
  - 공개 API·서버 그룹 골격 구현 완료. 다운로드·검증·교체는 미구현.
  - 다음 설계: 진행 정보 필드.
  - 확정 정책: 업데이트 준비 실패 시 종료 콜백을 호출하지 않음.
  - 검증 상태: 이번 변경은 빌드·실행 검증하지 않음.
```

작업 계획은 다음처럼 비운다. 다운로드 계획을 대신 채우지 않는다.

```markdown
# 작업 계획

## 현재 작업

진행 중인 작업 없음.

## 고정 방침

- 기존 데이터 마이그레이션은 하지 않는다.
- 빌드·실행 검증은 별도 요청이 있을 때 수행한다.
```

## 5. 다음 작업 조회와 큰 기능 완료

사용자: “이제 다음 작업은?”

- 전체 계획을 읽고 서버 통신 등 미완료 작업을 제안한다.
- 다음 작업을 승인받은 것처럼 코드 구현을 시작하지 않는다.
- 사용자가 구체적인 다음 계획을 요청할 때 작업 계획의 현재 작업을 새로 작성한다.
- 나중에 런처 업데이트 전체가 구현됐을 때 큰 항목을 [x]로 바꾼다. 빌드·실행 검증 상태는 실제 수행 여부를 별도 기록한다.

## 6. 단순 질문과 다른 프로젝트

사용자: “이 함수 이름은 무슨 뜻이야?”

설명만 하면 된다. 두 문서를 새로 만들거나 현재 작업을 재작성하지 않는다.

다른 프로젝트에서 계획 수립을 요청했다면 그 프로젝트의 문서를 찾는다. 위 예시의 마이그레이션 금지나 임시 폴더 위치를 자동으로 복사하지 않는다.
