# 시간과 메모리를 표시하는 순서도

측정을 요청받았을 때만 읽는다. 측정은 관찰이며 제품 최적화 승인이 아니다.

## 실행
- 실제 함수, 입력, 실행 환경을 확인한다. 입력을 바꾸는 작업은 테스트 사본으로 하고 회차마다 같은 시작 상태를 만든다.
- 기존 진단 기능, 테스트 실행 프로그램, 소스 사본에 측정점을 둔다. 알고리즘과 병렬도를 바꾸지 않는다.
- 실행할 수 없는 분기는 미측정으로 남긴다. 원본 삭제, 실제 게시, 외부 서비스 변경을 측정 때문에 실행하지 않는다. 기존 기록만 요청받았으면 다시 실행하지 않는다.

## 시간
- 단조 증가 타이머로 주요 경계를 재고 비동기 호출은 완료까지 기다린다. 너무 작은 단위로 재서 계측 비용이 결과를 덮지 않게 한다.
- 입력 복원, 빌드, 사후 확인은 본 측정에서 뺀다. 프로세스 시작·종료, 초기화, 큐 대기를 포함했는지 적는다.
- 기본 3회. 전체 시간 중앙값인 **실제 한 회차**를 대표로 쓴다. 단계별 중앙값을 조합한 가상 회차를 만들지 않는다.
- 반복·병렬 호출은 한 호출, 합산, 활동 구간 합집합(동시 호출이 겹친 시간은 한 번만 셈) 중 무엇인지 적는다. 노드 활동시간과 전체 경과시간은 다르다.

## 메모리
- 작업집합(Working Set, 실제 상주 페이지), 전용 메모리(Private Commit, 프로세스 전용 확보량), 누적 할당량을 구분한다.
- 구간 최대 전용 메모리는 그 구간에서 관측한 **프로세스 전체 값**이다. 그 함수만의 할당량으로 해석하지 않는다.
- 관측 주기, 단위, 대상·자식 프로세스 범위, 놓칠 수 있는 짧은 피크를 적는다. 겹치는 부모·자식과 병렬 영역의 시간·메모리는 합산하지 않는다.

## Canvas 표시
- 카드 본문 첫 줄에 `**시간 0.976초 | 최대 전용 29.07MB**`처럼 단위를 붙여 쓰고, 아래에 시나리오·횟수·측정 범위를 쓴다. 아주 짧으면 `<0.001초`로 쓴다.
- 함수·병렬 영역은 그룹 제목에 `클래스.함수 | 1.088초 | 최대 전용 29.07MB`처럼 짧게 쓴다. 함수 전체 수치는 시작 카드에도 적되 시작 처리 자체의 비용이 아님을 밝힌다.
- 실행하지 않은 분기는 `미실행`, 따로 재지 않은 조건은 `개별 미계측, 상위 구간에 포함`으로 쓴다. 0을 넣거나 부모 시간을 나눠 넣지 않는다.
- 조건이 다른 회차(예: 앱 업데이트, 최초 설치, 자체 업데이트)가 섞이면 카드마다 조건을 적는다.
- 메모리 피크 배지(`memoryPeak: observed`)는 대표 회차에서 반올림 전 같은 최고값이 관측된 **개별 노드**에만 붙인다. 그룹에는 붙이지 않는다. 다시 측정하면 대상을 새로 고른다. 함수 단독 할당량이나 증가 원인으로 단정하지 않는다.
- 상세 조건은 `.md`, 반복 비교 표는 `.base`로 연결한다. 원시 회차와 로그는 프로젝트 테스트 산출물 위치에 둔다.

## 기록과 보고
- 코드 기준(미커밋 변경 포함), 입력 규모, 장비·런타임, 작업자 수, 회차별 시간·메모리, 대표 회차, 계측 범위를 기록한다.
- 결과 정확성 확인과 성능 측정을 구분한다. 시간만 재고 기능 검증까지 통과했다고 말하지 않는다.
- 보고에는 대표 결과와 조건, Canvas 링크, 원시 결과 위치, 미측정 범위를 적는다.

## 해석 예시 (가상 수치)
전체 1.44초인 실행에서 병렬 영역이 1.09초이고, 다운로드 0.81초·적용 0.98초·검증 0.64초 활동이 있을 수 있다. 내부 활동은 겹치므로 합이 1.09초를 넘는 것이 정상이다. 세 영역의 최대 전용이 각각 28.5MB, 29.1MB, 29.1MB여도 전체 최대가 86.7MB라는 뜻이 아니며, 병렬 바깥 구간의 자체 피크를 쓴다.
