# Explain Code Changes

## 범위
- 코드 작업의 설명 방식에 적용한다. 코드 작성 규칙을 대신하거나 설명 요청을 수정·실행 권한으로 해석하지 않는다.
- 계획, 코드 정리 제안, 변경 이유·영향, 전후 비교, 자세한 작업 결과, 이해하기 어렵다는 피드백에 사용한다.
- 사용자가 코드만 요청하면 불필요한 설명을 붙이지 않는다. 단순 위치 확인·커밋 완료 보고·일반 대화에 긴 형식을 강제하지 않는다.
- 작은 변경은 짧게 설명한다. 모든 항목에 아래 틀을 기계적으로 반복하거나 추가 개선 작업을 억지로 제안하지 않는다.

## 공통 원칙
- 처음 등장하는 대상을 파일 → 클래스 → 함수·멤버와 연결한다. 예: `PatchInfo.cs`의 `PatchInfo.LoadFromJson()`. 이후에는 문맥이 명확하면 줄여 쓴다.
- "입력 검사", "작업 기록", "선정 결과" 같은 명사만으로 대상을 설명하지 않는다. 실제 코드가 있으면 관련 선언과 호출부를 확인하고, 제안한 이름은 아직 없는 제안임을 밝힌다.
- 현재 구현, 변경 제안, 적용 완료를 구분한다. 예시 코드의 생략·의사코드 여부도 밝히며, 설명 예시를 실제 수정 결과처럼 제시하지 않는다.
- 추상적인 평가보다 구체적인 상황과 결과로 이유를 설명한다. "검사가 늦다"보다 "실행 파일 이름을 잘못 입력해도 전체 압축 후 실패한다"가 낫다.
- 실제 동작 변경, 구조만 정리, 기능 제거를 구분한다. 그대로 유지되는 정책은 독자의 판단에 필요한 것만 설명한다.
- 핵심 영문 용어는 한국어 의미를 함께 설명하고, 약어는 처음에 전체 이름과 문맥상 의미를 밝힌다. 코드 식별자 자체를 모두 번역하지는 않는다.

## 작업별 설명

### 추가
필요한 상황 → 추가할 파일·클래스·함수 → 핵심 선언 또는 역할 → 사용 예와 기존 호출자 순서로 설명한다. 기존 구현이 없으면 억지로 전후 비교를 만들지 않는다.

### 수정
대상 위치 → 현재 방식 → 구체적인 문제 상황 → 변경 방식 → 달라지는 결과 순서로 설명한다. 전후는 같은 범위·표현·상세 수준으로 비교한다.

### 삭제
삭제 대상 → 기존 역할 → 필요 없어진 근거 → 남은 호출부·대체 경로 → 삭제 후 영향을 설명한다. 호출되지 않는다는 판단은 실제 참조와 외부 공개 여부를 확인한다. 기능 자체를 없애는지 중복 구현만 없애는지 구분한다.

### 조합: 이동·공통화
하나의 목적 아래 추가·수정·삭제를 연결한다. 출발지와 도착지, 새 호출자, 제거되는 구현을 명시한다. 서로 떨어진 변경 파일 목록만으로 설명을 대신하지 않는다.

## 표현 선택
| 설명 대상 | 우선 표현 |
| --- | --- |
| 실행 순서·조건·반복·실패·취소 | 현재/변경 후 알고리즘 |
| 함수 이름·인자·반환형·호출 | 핵심 코드 선언과 호출 예 |
| 중복 제거·책임 이동 | 파일·함수 간 이동 및 호출 관계 |
| 클래스 소유·상속·참조 | 책임 비교 또는 클래스 관계도 |
| 파일 배치·출력 경로 | 폴더 트리 |

- 짧은 알고리즘 비교는 들여쓴 단계와 화살표로 충분하다. 전체 코드를 붙여 실행 흐름 설명을 대신하지 않는다.
- Mermaid 순서도, 클래스 관계도, 폴더 트리가 필요하고 해당 스킬이 제공되어 있으면 각각 `algorithm-flowchart`, `class-diagram`, `text-tree`를 참고한다. 없으면 요청 형식에 맞춰 직접 표현한다.
- 그림은 설명을 돕는 경우에만 추가한다. 사용자가 지정한 표현 방식을 우선한다.

## 예시 참고
구체적인 작성 예가 필요하거나 설명을 쉽게 다시 풀어달라는 요청에는 [references/examples.md](references/examples.md)의 해당 작업 예시를 읽는다. 예시는 설명용 가상 코드이며 특정 프로젝트의 구조나 정책을 다른 프로젝트에 강제하지 않는다.
